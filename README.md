# SnapGit

SnapGit — небольшая консольная программа на Python для создания и восстановления
снимков рабочего дерева Git-проекта. Она получает списки файлов через Git,
применяет отдельные правила `.snapignore` и копирует выбранные файлы в каталог
резервной копии с сохранением исходной структуры папок.

Программа не изменяет историю Git и не заменяет `git pull`, `git push`, DVC или
полноценную систему резервного копирования. Она создаёт независимую файловую копию
с диагностическими списками.

## Возможности

- резервное копирование явно указанного Git-проекта;
- включение отслеживаемых, неотслеживаемых и игнорируемых Git файлов;
- независимая фильтрация через `.snapignore`;
- сохранение структуры каталогов проекта;
- корректная обработка пробелов и Unicode в путях;
- защита от создания рекурсивного бэкапа внутри проекта;
- безопасное восстановление untracked и ignored файлов после `git clone` или
  `git pull`;
- полное восстановление сохранённого Git commit и рабочего дерева, включая
  локально изменённые tracked-файлы и намеренно удалённые файлы;
- проверка размера и SHA-256 каждого обычного файла перед полным восстановлением;
- сохранение символических ссылок и файловых прав;
- отдельный журнал файлов, которые исчезли или не скопировались;
- краткая статистика после завершения.

## Требования

- Windows 10/11;
- Python 3.9 или новее;
- Git, доступный через `PATH`.

Сторонние Python-библиотеки не требуются.

В корне проекта, который нужно скопировать, обязательно должны находиться:

```text
.git\              каталог репозитория
.gitignore         файл, может быть пустым
.snapignore        файл, может быть пустым
```

`ProjectRoot` должен указывать непосредственно на корень репозитория, а не на его
вложенную папку. Git worktree, где `.git` является файлом, текущей версией программы
не поддерживается.

## Запуск

Рекомендуемый вариант параметров:

```powershell
python .\SnapGit.py backup `
    "D:\Projects\MyProject" `
    --snap-root "E:\Backups"
```

Короткий вариант параметра каталога снимков:

```powershell
python .\SnapGit.py backup `
    "D:\Projects\MyProject" `
    -sr "E:\Backups"
```

В режимах `backup` и `restore` путь проекта — обязательный позиционный аргумент
`PROJECT_ROOT`. Для текущего каталога можно использовать точку:

```powershell
python .\SnapGit.py backup .
```

Каталог снимков можно задать переменной окружения `SNAP_ROOT`. Тогда параметр
`--snap-root` не нужен:

```powershell
$env:SNAP_ROOT = "E:\Backups"
python .\SnapGit.py backup "D:\Projects\MyProject"
```

Явно переданный `--snap-root` или `-sr` имеет приоритет над `SNAP_ROOT`. Если путь
не задан ни одним из этих способов, программа завершится с ошибкой параметров.

## Повторение структуры проектов

Необязательный параметр `--source-root` задаёт общий корень дерева проектов. Путь
от него до `ProjectRoot` повторяется внутри `SnapRoot`.

Например:

```powershell
$env:SNAP_SOURCE_ROOT = "D:\aLX\CodeWorks\Pycharm"
$env:SNAP_ROOT = "D:\aLX\CodeWorks\Archive"

python .\SnapGit.py backup `
    "D:\aLX\CodeWorks\Pycharm\Wrk\SnapGit"
```

Снимок будет создан внутри:

```text
D:\aLX\CodeWorks\Archive\Wrk\SnapGit\
```

Вместо переменной `SNAP_SOURCE_ROOT` путь можно передать явно:

```powershell
python .\SnapGit.py backup `
    "D:\aLX\CodeWorks\Pycharm\Wrk\SnapGit" `
    --source-root "D:\aLX\CodeWorks\Pycharm" `
    --snap-root "D:\aLX\CodeWorks\Archive"
```

Явный `--source-root` имеет приоритет над `SNAP_SOURCE_ROOT`. Если общий корень не
задан, программа использует прежнюю плоскую структуру `<snap-root>\<project>`. Если
`ProjectRoot` не находится внутри заданного `SourceRoot`, программа завершится с
ошибкой, не создавая снимок.

## Ежедневное уплотнение

Параметр `--compact-day` или его короткая форма `-cd` запускает уплотнение после
успешного создания нового снимка:

```powershell
python .\SnapGit.py backup `
    "D:\aLX\CodeWorks\Pycharm\Wrk\SnapGit" `
    --compact-day
```

Программа просматривает все проекты внутри `SnapRoot`. Если у проекта за один день
есть несколько снимков, в основном архиве остаётся только самый поздний снимок по
имени каталога `HH-mm-ss`. Более ранние снимки перемещаются в `$purge$` с сохранением
полного относительного пути.

Например:

```text
<snap-root>\Wrk\SnapGit\2026-08-30\12-10-00
```

будет перемещён в:

```text
<snap-root>\$purge$\Wrk\SnapGit\2026-08-30\12-10-00
```

Дополнительные каталоги `Arc` или `Hst` не создаются. Каталог `$purge$` исключается
из повторного просмотра. Если путь назначения в `$purge$` уже существует, программа
не перезаписывает его и завершает уплотнение с ошибкой. Если новый снимок создан не
полностью и программа возвращает код `2`, уплотнение не запускается.

## Месячное уплотнение

Параметр `--compact-month` или его короткая форма `-cm` задаёт границу месячной
уборки. Для каждого проекта программа обрабатывает все месяцы до этой границы
включительно, оставляя в каждом месяце только самый поздний снимок. Остальные снимки
перемещаются в `$purge$` по тем же правилам, что и при ежедневном уплотнении.

Число после параметра задаёт смещение относительно текущего месяца:

- `-cm 0` — уплотнить все месяцы по текущий включительно;
- `-cm -1` — уплотнить все месяцы по предыдущий включительно, не трогая текущий;
- `-cm -2` — уплотнить все месяцы по месяц перед предыдущим включительно;
- `-cm` без числа — уплотнить все месяцы по месяц шестимесячной давности
  включительно, то есть использовать значение `-6`.

Например:

```powershell
python .\SnapGit.py backup `
    "D:\aLX\CodeWorks\Pycharm\Wrk\SnapGit" `
    -cm -1
```

Поскольку число после `-cm` необязательно, при запуске без числа путь проекта нужно
указывать перед `-cm`:

```powershell
python .\SnapGit.py backup . -cm
```

Месяцы после рассчитанной границы и вплоть до текущего не изменяются. Для определения
последнего снимка каждого обрабатываемого месяца сравниваются сначала имена каталогов
дней `YYYY-MM-DD`, затем имена каталогов времени `HH-mm-ss`. Положительные смещения
не поддерживаются. Если одновременно заданы `--compact-day` и `--compact-month`,
сначала выполняется ежедневное, а затем месячное уплотнение.

## Восстановление локальных файлов после `git clone` или `git pull`

По умолчанию команда `restore` работает в безопасном режиме `extras`: восстанавливает
только локальные файлы, которые во время создания снимка относились к untracked или
ignored:

```powershell
python .\SnapGit.py restore `
    "D:\Projects\MyProject" `
    --snapshot "D:\Backups\Wrk\MyProject\2026-08-30\18-44-08"
```

Перед реальным восстановлением рекомендуется посмотреть план:

```powershell
python .\SnapGit.py restore `
    "D:\Projects\MyProject" `
    --snapshot "D:\Backups\Wrk\MyProject\2026-08-30\18-44-08" `
    --dry-run
```

Кандидаты определяются как пересечение `untracked.lst` и `ignored.lst` с итоговым
`backup-files.lst`. Благодаря этому не восстанавливаются файлы, исключённые через
`.snapignore`.

Правила безопасности:

- файлы, которые теперь отслеживаются Git в целевом репозитории, никогда не
  перезаписываются;
- уже существующие untracked или ignored файлы считаются конфликтами;
- `--overwrite` разрешает замену существующих локальных файлов, но по-прежнему не
  затрагивает tracked-файлы и символические ссылки назначения;
- снимок с `copy-errors.lst` по умолчанию отклоняется; параметр
  `--allow-incomplete` разрешает восстановить доступную часть;
- абсолютные пути, `..` и пути, выходящие за пределы проекта или каталога `backup`,
  отклоняются;
- режим ничего не удаляет и не требует наличия `.snapignore` в новом клоне.

Старые снимки формата `Arc`/`Hst` без каталога `backup` и диагностических `.lst`
этим режимом не поддерживаются.

## Полное восстановление рабочего дерева

Новые снимки можно использовать для восстановления не только локальных extras, но
и полного состояния файлов на момент снимка:

```powershell
python .\SnapGit.py restore `
    "D:\Projects\MyProject" `
    --snapshot "D:\Backups\Wrk\MyProject\2026-09-03\12-00-00" `
    --mode full `
    --dry-run
```

Если план верен, повторите команду без `--dry-run`. Полный режим:

1. Проверяет `snapshot.json`, размеры и SHA-256 сохранённых обычных файлов, а также
   цели символических ссылок.
2. Проверяет наличие сохранённого Git commit и требует полностью чистое целевое
   рабочее дерево, включая отсутствие untracked-файлов.
3. Переключает репозиторий в состояние `detached HEAD` на сохранённом commit.
4. Накладывает поверх него все файлы снимка: tracked, untracked и ignored.
5. Повторяет намеренные удаления tracked-файлов и восстанавливает сохранённые
   символические ссылки и файловые права.

Если commit отсутствует в новом клоне, сначала получите его из удалённого
репозитория, например `git fetch --all --tags`, и повторите восстановление. SnapGit
не выполняет сетевую загрузку автоматически.

Существующие untracked и ignored пути считаются конфликтами; `--overwrite`
разрешает их заменить. Любой конфликт обнаруживается до переключения commit.
Снимок со статусом `incomplete` по умолчанию отклоняется; `--allow-incomplete`
разрешает попытаться восстановить доступную часть.

`snapshot.json` сохраняет списки staged и unstaged путей, но полный режим пока не
восстанавливает границу индекса Git: все локальные изменения оказываются в рабочем
дереве после чистого checkout. Старые снимки без `snapshot.json` поддерживают только
режим `extras`.

Общая справка и справка по отдельным режимам:

```powershell
python .\SnapGit.py --help
python .\SnapGit.py backup --help
python .\SnapGit.py restore --help
```

## Структура результата

Если задан `SourceRoot`, относительный путь проекта определяется от него. Иначе
используется только имя каталога `ProjectRoot`. Для каждого запуска создаётся
отдельная папка даты и времени:

```text
<snap-root>\
└── <relative-project-path>\
    └── YYYY-MM-DD\
        └── HH-mm-ss\
            ├── tracked.lst
            ├── untracked.lst
            ├── ignored.lst
            ├── backup-files.lst
            ├── copy-errors.lst       создаётся только при ошибках
            ├── snapshot.json         записывается последним
            └── backup\
                └── ...               файлы проекта с исходной структурой
```

Списки имеют следующее назначение:

- `tracked.lst` — результат `git ls-files`;
- `untracked.lst` — неотслеживаемые и неигнорируемые Git файлы;
- `ignored.lst` — неотслеживаемые, но игнорируемые Git файлы;
- `backup-files.lst` — итоговый список после применения `.snapignore`;
- `copy-errors.lst` — отсутствующие файлы и ошибки копирования.

`snapshot.json` содержит версию формата, признак полноты снимка, исходный путь
проекта, Git HEAD, ветку и `remote.origin.url`, списки staged, unstaged и удалённых
tracked-путей, а также метаданные каждого скопированного файла: категорию, размер,
SHA-256, права и данные символической ссылки. Он записывается последним, поэтому его
наличие означает, что формирование снимка дошло до завершающего этапа.

Первые три списка сохраняют исходный результат Git. Поэтому в них могут быть пути,
которые исключены из резервной копии. Реальному содержимому папки `backup`
соответствует `backup-files.lst`.

## Файл `.snapignore`

`.gitignore` определяет, что отслеживает Git. `.snapignore` независимо определяет,
что не следует помещать в резервную копию. Благодаря этому крупный файл может быть
исключён из Git, но всё равно включён в бэкап.

Пример:

```gitignore
# Служебные каталоги в любом месте проекта
.git/
.idea/
.vscode/
__pycache__/
.ruff_cache/
.pytest_cache/
.mypy_cache/

# Служебные файлы
*.pyc
*.pyo
*.tmp

# Каталог только в корне проекта
/local-cache/

# Вернуть ранее исключённый файл
!important.tmp
```

Поддерживаемые правила:

- пустые строки и строки с `#` игнорируются;
- `name/` исключает каталог с таким именем на любом уровне;
- `/name/` привязывает правило к корню проекта;
- `*` соответствует символам, кроме разделителя каталогов;
- `**` может соответствовать нескольким уровням каталогов;
- `?` соответствует одному символу;
- `!pattern` повторно включает путь;
- более позднее правило имеет приоритет над более ранним;
- сравнение путей в Windows выполняется без учёта регистра.

Это намеренно ограниченное и понятное подмножество синтаксиса `.gitignore`, а не его
полная реализация.

## Какие файлы попадают в обработку

SnapGit объединяет без дубликатов результаты трёх команд:

```text
git ls-files
git ls-files --others --exclude-standard
git ls-files --others --ignored --exclude-standard
```

После этого объединённый список фильтруется через `.snapignore`.

## Коды завершения

- `0` — операция выполнена полностью;
- `1` — ошибка параметров, структуры проекта, Git или создания назначения;
- `2` — снимок или восстановление выполнены частично: некоторые файлы не удалось
  скопировать либо обнаружены конфликты.

При неполном снимке подробности находятся в `copy-errors.lst`; при восстановлении
они также выводятся в консоль.

## Важные замечания

- `SnapRoot` должен находиться вне копируемого проекта.
- `--compact-day` перемещает лишние снимки в `<snap-root>\$purge$`, но не удаляет их.
- `--compact-month` в каждом месяце до рассчитанной границы оставляет один последний
  снимок, а остальные перемещает в `<snap-root>\$purge$`, не удаляя их.
- Если два запуска произошли в одну секунду, второй завершится с ошибкой, не
  перезаписывая первый снимок.
- Файлы могли измениться или исчезнуть между получением списка Git и копированием;
  такие случаи отражаются в `copy-errors.lst`.
- Ошибка доступа к отдельному файлу, включая заблокированные или недоступные
  символические ссылки, записывается в `copy-errors.lst`; обработка остальных файлов
  продолжается, а программа завершается с кодом `2` без Python traceback.
- Для создания символических ссылок при полном восстановлении Windows может
  потребовать режим разработчика или запуск с соответствующими правами. Если права
  не выданы, ошибка попадёт в итоговую статистику, а программа вернёт код `2`.
- Синхронизация облачного каталога не заменяет отдельный бэкап: удаление или
  повреждение может распространиться на другие компьютеры.
